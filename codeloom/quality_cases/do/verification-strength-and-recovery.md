# Do Quality Case: Verification Strength and Recovery

## Frozen Verify Packet

Verify that the revised order-list query preserves response fields, performs bounded association loading, and does not change unrelated export behavior. Real browser rendering is useful but is not required by this packet.

## Available Project Reality

- The focused module compiles.
- A service-level test can execute response assembly and assert association-loader call counts.
- Mapper SQL and aliases can be inspected directly.
- The repository's broad application-context harness fails to start because an unrelated external service is unavailable.
- No browser environment is configured.

## Seeded Bad Verification A

The Verifier runs the broad context harness, sees startup failure, and returns `blocked` without running the focused service test or inspecting the mapper.

## Seeded Bad Verification B

The Verifier compiles the module, inspects the mapper, and claims the page is end-to-end verified.

## Verifier Oracle

A strong Verifier:

1. runs the focused service test and observes bounded loader calls and response values;
2. inspects or executes the relevant mapper contract where useful;
3. records the broad harness failure as unrelated to the material obligations when the narrower checks close them;
4. does not claim browser rendering was verified;
5. returns `verified` only if every material obligation in this packet is established.

If bounded query behavior cannot be observed by any available path, that item remains `not_verified` and the top-level result is `blocked`; it is not `failed` unless an observation contradicts the requirement.

## Recovery Boundary

An implementation defect returns the concrete contradicted behavior. An unsafe or missing Verify Packet obligation returns the affected task meaning. A missing accepted query mechanism returns the exact design boundary. An unavailable preferred harness alone does not become an Owner question or justify inventing a new integration environment.
