# Phase 1：Spec Analyzer 需求收敛

## 目标

`spec-analyzer` 将不完整、混合或带方案倾向的人类描述，收敛为可直接进入技术设计的 AI-Coding 需求决定。

完成后的 `spec.md` 应让后续阶段理解：现实中什么必须改变、谁受到影响、什么事实和规则决定正确性、哪些结果不能发生，以及未来观察到什么才能证明目标成立。

## 核心能力

### 1. 恢复真实需求

人类描述可能同时包含：

```text
目标、症状、局部功能、候选方案、偏好、约束、历史背景和担忧
```

Analyzer 不逐句照收，而是判断每项表达在需求中的作用，并恢复：

- 改变为什么必要；
- 哪个角色或系统受到影响；
- 当前产生了什么错误、不完整、危险或误导性结果；
- 目标现实中必须建立什么结果；
- 哪些显式承诺和有证据支持的隐含承诺不可丢失。

页面、接口、字段、Job、表、按钮和实现建议只是需求线索，不能自动替代真实结果。未确认偏好不成为硬需求。

材料承诺是指：遗漏或改变其含义，会使目标结果不再成立的承诺。复杂需求保全全部材料承诺；小型闭合修复只分析其实际结果和直接风险。

### 2. 使用判别性证据

调查的目标不是收集更多资料，而是区分会改变需求判断的可信解释。

对每项材料结论，应明确：

```text
它依据什么；
该证据证明什么；
不能证明什么；
是否存在冲突证据；
新事实将如何改变当前判断。
```

必须区分：

- 已被接受输入或可观察证据支持的事实；
- 有证据基础但仍可被反驳的推断；
- 描述当前现实、但不自动定义目标的当前行为；
- 证据无法代替的 Owner 选择。

代码、数据、接口、测试、截图、记录和局部成功都只能证明其直接观察到的事实。证据不足不能被写成已确认实现缺陷，现有路径也不能仅因存在就被判定为正确承接。

材料事实应在相关证据可获得时完成裁决，不能直接输出泛化的“未知”。只有经过定向调查后事实仍未证实，并且目标需求不依赖该事实答案时，才保留 evidence gap；同时说明现有证据为什么不足、哪项判断尚不成立、当前不能假设什么，以及什么证据能够解决它。如果缺失事实会阻止正确的需求决定，则停止最终 Spec 并返回所需证据。Evidence gap 描述当前现实的证明边界，不能替代对材料承诺本身的需求判断。

### 3. 理解当前与目标的因果差异

只重放会改变正确性的场景：

```text
触发或输入
→ 决定行为的事实、判断或状态
→ 责任与处理
→ 数据、状态或外部后果
→ 可观察结果与反馈
```

通过当前现实与目标现实的比较，识别：

- 信息或责任丢失；
- 重复处理与冲突；
- 错误状态语义；
- 局部成功形成的虚假完成；
- 仍然可达的禁止副作用；
- 目标结果无法被观察或追溯。

这是一种因果判断方式，不是固定流程表。简单需求通常只需一个闭合场景；复杂需求只增加真正会改变需求正确性的场景。

### 4. 裁决材料承诺

每项材料承诺都要形成有证据的可读结论：

- 是否是目标成立所必需；
- 是否已有可达路径被证据证明正确承接；
- 是否有已确认规则与当前可达行为冲突；
- 是否需求已成立但当前现实仍缺证据；
- 是否已有清楚的范围边界或在其他位置被满足；
- 是否与当前目标无关；
- 是否仍取决于 Owner 选择。

这些是判断差异，不是固定字段、编号或 artifact 格式。最终内容应形成一个连贯需求决定，而不是内部分类清单。

### 5. 以 Goal / Way / Proof 收敛

```text
Goal：必须建立的真实用户或系统结果。
Way：约束该结果的事实、规则、语义、责任、权限、范围和禁止后果。
Proof：未来可以建立或反驳该结果的可观察事实及证据强度。
```

Goal / Way / Proof 是推理透镜，不是 Markdown 固定标题。

Proof 关注结果而非实现表面的存在。页面显示、接口响应、编译、截图、mock 或局部测试只证明其直接观察到的事实。

### 6. 有限 Owner 澄清

先调查可调查事实。未经证明安全或适用的候选方法不是 Owner 选择：Analyzer 应分离目标与方法，保留必要的安全和后果边界，不能让 Owner 代替事实判断。一个候选方法加上缺失证据，不构成两个可信需求方向；此时应明确目标结果和禁止后果，并让方法保持开放。

只有同时满足以下条件，才需要 Owner 决定：

- 已接受输入或证据主动支持两个或更多可信且互不兼容的需求含义或业务规则；
- 证据不能决定应采用哪个方向；
- 选择会改变目标、范围、验收含义、公开含义、数据或状态语义，或者允许的外部后果。

一次只提出一个最高信息量决定，并提供已证实事实、可信方向、影响和当前最有依据的建议。普通实现选择和缺失证据不进入需求澄清。

未解决且仍改变需求正确性的 Owner 选择不能被猜测或隐藏在最终 `spec.md` 中。

### 7. Reviewer 反证

`spec-reviewer` 不复建完整需求分析，只针对具体草案判断构造最小证据反例。反证聚焦：

- 材料承诺丢失；
- 结论超出证据；
- 因果链缺失导致错误结果或虚假完成；
- 未经授权选择 Owner 方向。

Analyzer 根据证据吸收或拒绝 finding，并保留最终需求判断。

## Spec 产物

最终 `spec.md` 应以最适合当前需求的形式清楚表达：

- 当前现实与目标结果；
- 判断依据、局限和材料冲突；
- 会改变正确性的场景与因果后果；
- 每项材料承诺的当前结论；
- 约束结果的事实、规则、含义、责任、权限、范围和禁止后果；
- 可观察成功、材料失败或边界行为，以及相称的 Proof direction。

完成标准是需求决定已经连贯、可审阅，并足以进入技术设计；不是填完固定章节或输出分析过程。

## 非目标

Spec 不产生技术架构、表/API/SQL/事务/类/UI 组件设计，不拆任务，不执行验证，不作发布结论，也不持久化内部推理过程。

Agent 调用、定向调查、Owner 交互、artifact 写入与状态登记由现有运行层承担，不进入 Agent 的需求语义 Prompt。

## 验收场景

| 场景 | 预期表现 |
|---|---|
| 复杂业务需求同时包含多个结果和一个指定方案 | 保全材料承诺，恢复指定方案背后的真实目标，以证据和因果场景裁决当前现实，不照抄方案。 |
| 单字段或单规则修正 | 直接收敛错误事实、正确来源、影响范围和证明方向，不扩张成领域重构或多余澄清。 |
| 当前代码、测试和业务描述冲突 | 保留各来源的证明边界，不把具体代码或局部测试升级为业务真相。 |
| 状态与外部结果不同步 | 区分动作、处理中状态、外部事实、完成结果、失败与反馈，避免虚假完成。 |
| 两个可信业务方向无法由证据裁决 | 不静默选边，只提出一个会改变需求正确性的 Owner 决定。 |
