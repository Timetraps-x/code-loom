# Spec 阶段：目标与方式

## 1. 定位

Spec 阶段将原始需求加工为**本轮已确认的目标集合**及其**不可擅改的方式边界**，使后续 `plan` 不需要猜业务意图、范围或风险接受。

它不是需求转述器，不是技术方案，不是 build / verify 任务计划，也不是未来 release 路线图。

```text
原始需求
→ 探索需求相关事实与业务跨度
→ 拆出可独立承诺的目标
→ 确认本轮目标集合
→ 收敛目标边界、方式边界与完成含义
→ 交给 plan
```

## 2. 两层目标与方式

必须区分 spec 阶段自身的目标与需求本身的目标。

| 层次 | 目标 | 方式 |
|---|---|---|
| Spec 阶段 | 形成不遗漏、不臆测、可被正确设计的需求决策 | 保留原始诉求、证据探索、目标拆分、范围判断、有限澄清与覆盖检查 |
| 本轮需求 | 改变已确认的用户或系统结果 | 遵守业务规则、数据语义、范围、非目标和关键约束 |

前者决定 spec 如何工作；后者约束 plan、tasks 和 do 可以怎样完成需求。

## 3. Spec 阶段要解决的内容

### 3.1 保真理解原始诉求

原始需求、背景资料、已知问题、明确限制和历史上下文都是输入证据，不能被 AI 的目标重述覆盖或压缩掉。

先区分：

- **目标**：希望改变的用户或系统结果；
- **实现建议**：用户提出的可能做法；
- **现状或缺陷**：系统当前行为，不自动等于目标行为；
- **约束**：已明确的范围、性能、兼容、数据或外部系统限制；
- **未知**：会影响目标选择或允许方式、但证据无法决定的事项。

### 3.2 围绕需求探索必要跨度

探索目标不是完成领域百科，而是避免遗漏会影响目标成立、范围或方式的事项。

业务需求通常从目标向外探索：

```text
角色与权限
→ 业务对象与事实来源
→ 前置条件和动作
→ 状态及其后果
→ 可见性与反馈
→ 数据或外部副作用
→ 相邻流程和高后果风险
```

技术需求通常从目标向外探索：

```text
触发条件
→ 处理集与排除集
→ 事实主权
→ 当前行为或缺陷
→ 正确结果
→ 数据/状态/外部副作用
→ 一致性、性能、并发、恢复和兼容影响
```

探索应停止在以下问题已能回答时：

1. 当前要改变的结果是什么；
2. 哪些事实、条件、状态和后果使该结果有效；
3. 已发现的相关事项在本轮如何处理；
4. 哪些方式不可接受；
5. 后续需要证明什么。

不改变这些答案的实现细节留给 `plan` 或 `do`。

### 3.3 区分事实、推断、历史与决策

| 分类 | 含义 |
|---|---|
| 已证实事实 | 由代码、数据、配置、文档、测试或运行证据支持 |
| 合理推断 | 被证据支持但仍可能被推翻的解释 |
| 历史行为 / 已知缺陷 | 系统当前做法，不自动代表应继续保持的目标行为 |
| Owner 决策 | 会改变结果、语义、范围、公开契约或风险接受，且不能由证据决定的选择 |

优先查证。只有无法由证据解决、且会改变需求正确性的未知，才交给 owner。

## 4. 拆分目标：拆需求结果，不拆实现

大需求必须拆出目标候选，防止 AI 以页面、接口、表或技术层替代业务结果。

```text
原始需求：建设售后域

目标候选：
G1：问题可被发起并进入售后处理；
G2：已受理问题可派给处理人并受时限管理；
G3：问题可形成检测、判责和证据结论；
G4：结论可推进维修、费用、退款或换货；
G5：处理结果可结案、评价和统计。
```

目标候选的拆分依据是：

- 是否代表不同的用户或系统结果；
- 是否可以被独立承诺、拒绝、延期或验证；
- 是否涉及不同的业务 owner、规则、风险或证明边界。

小而闭合的需求不强拆。例如“修复订单导出中客户名称取错字段”可以只有一个目标。

Spec 不拆：

```text
建表 → Service → API → 页面 → 测试
```

这些属于后续的实现组织，不是需求目标。

## 5. 选择本轮目标：证据优先，必要时 AskUserQuestion

Spec 先基于用户输入、业务资料、当前代码、数据、配置、同类流程、历史和运行证据判断：

- 哪些目标必须一起完成，当前结果才成立；
- 哪些目标已有机制承接；
- 哪些可作为后续目标；
- 哪些目标依赖尚未确定的规则或风险接受。

当证据已足以得出本轮目标时，直接收敛，不为形式而提问。

当目标选择会改变用户结果、数据语义、公开契约、范围、发布风险或资源投入，且证据无法决定时，必须使用 `AskUserQuestion`。提问必须提供已调研的候选、影响和推荐，而不是将判断推回用户。

```text
已确认：
- G1 可独立让问题进入售后处理；
- G2 依赖尚未明确的派单规则；
- G3-G5 不影响 G1 当前闭合。

候选：
A. 承诺 G1：申请 → 待受理 → 受理 → 状态反馈（推荐）
B. 承诺 G1 + G2：同时交付派单与时限
C. 仅支持申请创建（不推荐，不能保证进入处理）
```

用户确认的是本轮承诺的目标或目标集合，不是表结构、任务、SQL 或局部实现。

## 6. 收敛方式：方法 + 规范

目标确定后，spec 要定义达成目标时不能被下游以“更方便、更通用、更安全”为理由擅改的边界。

Spec 必须收敛：

- **业务规则**：谁能做、何时能做、重复时如何处理；
- **数据语义与事实主权**：哪个对象或字段是事实来源，数据代表什么；
- **状态与权限**：哪些状态可进入、谁能推进、谁能看见；
- **范围与副作用**：本期不能创建、调用、更新或触发什么；
- **关键约束**：已明确会改变可接受语义、范围、副作用或风险的性能、一致性、事务、迁移、兼容、合规或外部系统限制。

例如 SIM 服务期同步：

```text
只处理满足条件且已有订单关联的记录；
不补缺失订单；
不查询 ERP；
不更新未授权字段；
不为未定义脏数据增加修复或兜底语义；
不引入未约定的默认 batch 行为；
不得采用突破既定处理边界的更新方式。
```

这些是需求层方式边界，不是 plan 可任意替换的建议。

Spec 不决定可替换的技术设计，例如表结构、接口、SQL 组织、事务实现、批次大小、索引、缓存、类结构或页面布局，除非当前需求明确把它们定为不可协商约束。

## 7. 定义完成含义与证明方向

Spec 不执行验证，但必须规定后续要证明的结果：

```text
成功：谁在什么情境下能观察到什么结果；
失败 / 边界：越权、重复、异常、排除情况如何处理；
证明方向：结果需要何种强度的证据。
```

证明强度按风险适配：

| 风险形态 | 最低有意义的证明方向 |
|---|---|
| 局部静态事实 | 静态检查或定向自动化检查 |
| 规则、映射、计算 | 示例和边界断言 |
| 用户动作、权限、状态、反馈 | 真实入口 → 动作 → 状态/数据或副作用 → 可见反馈 |
| 数据同步、迁移、性能、并发、恢复 | 数据核对、重复执行、测量、执行计划或实验 |
| 外部系统或业务结果 | 集成证据、人工确认或发布后观察 |

页面渲染、HTTP 200、编译通过或孤立测试通过，不能替代它未实际观察到的高后果目标。

## 8. 覆盖检查

探索中发现的每个会改变当前目标判断的事项，必须得到结论：

| 事项结论 | 含义 |
|---|---|
| 当前必要 | 不纳入则本轮目标不成立 |
| 既有承接 | 由现有机制正确提供，需有证据 |
| 当前排除 | 相关但本轮不承诺，说明原因和边界 |
| 调研无关 | 已有依据表明不影响当前目标 |
| Owner 决策 | 无法由证据解决，需带候选、影响和推荐澄清 |

没有结论的事项是遗漏风险，不能因当前实现不方便而静默丢弃。

## 9. 交给 Plan 的需求决策

Spec 的输出不是任务计划，而是一份需求决策：

```text
原始需求及来源；
已识别目标候选与目标选择依据；
本轮确认承诺的目标集合；
使当前目标成立的必要业务/技术跨度；
相关但未承诺目标的范围结论；
已证实事实、合理推断和历史/缺陷行为；
不可擅改的方式边界；
成功、失败与证明方向；
仍需 owner 决定或明确属于技术设计的未知。
```

`plan` 必须在这些目标与方式边界内选择实现方案。新证据若改变目标、语义、范围或风险接受，应返回 `spec`，不能由 `plan`、`tasks` 或 `do` 静默决定。

## 10. 明确不负责

Spec 不负责：

- 将目标拆成 build / verify task；
- 决定任务顺序、依赖、执行 lane 或并行方式；
- 制定未来 release 的执行路线图；
- 设计表、接口、SQL、事务、索引、类结构或 UI；
- 将存量实现自动视为正确需求；
- 将普通工程常识堆成非目标；
- 因小需求强制完整领域建模；
- 将可由证据推导的问题交给用户。

## 11. 一句收敛

```text
Spec 拆目标，不拆实现；
Spec 通过证据与必要的 AskUserQuestion 确认本轮目标；
Spec 交给 plan 的是目标集合及其不可擅改的方式边界，
使后续能够高质量地设计、拆任务、实现和证明。
```
