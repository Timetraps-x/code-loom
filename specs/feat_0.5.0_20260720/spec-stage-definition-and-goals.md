# Spec 阶段：定义与目标

## 定义

Spec 阶段将不完整、含糊、可能遗漏或相互矛盾的自然语言需求，结合业务背景、业务场景、受影响的完整业务或技术链路、项目上下文、当前系统事实、历史材料和必要澄清，收敛为 AI-Coding 工作流可正确推进的需求。

自然语言需求是问题、意图、现象、偏好和约束的输入线索，不是可直接执行的完整真值。Spec 负责发现、分析、区分和表达；不负责替业务决定取舍。

## 目标

使后续阶段不必重新猜测以下问题：

- 要解决什么业务或产品问题；
- 谁在什么场景下受到影响；
- 哪些功能点、规则、事实、约束和结果共同构成该需求；
- 当前系统已经承接什么、与目标冲突什么、还缺少什么证据；
- 哪些结论已确认，哪些只是候选推断，哪些必须由有权决定者确认；
- 什么可观察结果说明需求达成，什么反例说明没有达成。

## 收敛内容

### 业务背景

说明问题为何出现、影响哪些角色或系统、当前现实和项目约束是什么。业务需求和技术需求都需要背景：前者关注业务与用户工作，后者关注运行、演进、性能、兼容或可靠性问题。

### 业务场景

识别会改变正确性的角色、触发条件、状态、数据规模、权限、异常和决策变化。场景既包括正常处理，也包括重复、失败、终止、恢复、交接或后续变化等相关路径。

### 受影响的完整链路

理解从触发、判断、处理、协作、状态或数据变化，到结果、反馈和追溯的必要链路。

“完整”只指与目标达成、用户结果或错误风险直接相关的链路，不要求穷举整个业务域，也不能只实现最显眼的局部功能点。

### 完整业务与产品目标

从输入和证据中挖掘所有已发现的重要目标、隐含承诺、功能点及其依赖关系。

- **业务视角**：结果、规则、角色责任、状态、事实主权和不可破坏的业务不变量是否正确；
- **产品视角**：用户能否方便、清楚、可靠、高效地完成工作，是否存在重复操作、不可理解反馈、权限障碍、性能或恢复问题；
- **质量约束**：仅保留由需求、项目上下文或受影响链路支持的性能、兼容、数据、一致性、安全、可维护性等要求。存量项目与新项目应按各自上下文理解，不能套用统一清单。

功能点的分析用于理解完整业务，不等同于技术设计、任务拆分或 AI 自行决定迭代范围。

### 当前系统现实

核对当前可达路径、状态、数据、外部副作用、用户可见结果和历史决策。

必须区分：

- 已证实的需求目标或规则；
- 当前系统事实；
- 当前实现与已确认规则的冲突；
- 规则成立但现状、样本或验证不足的证据缺口；
- AI 基于上下文提出的候选推断；
- 不能由证据决定、需要有权决定者确认的事项。

代码、测试、历史任务完成、页面展示或局部成功记录，只能证明其实际覆盖的事实，不能自动证明完整业务目标已经达成。

### 授权边界与不确定性

AI 可以发现目标、隐含约束、冲突、候选场景和待澄清问题；可以通过项目材料验证或反驳输入中的假设。

复杂需求可以按需使用可读标签辅助 Plan、Tasks 和人工定位某项承诺；标签不是 ID、schema 或跨 revision 谱系协议。承诺是否保全取决于其语义去向、边界与证据，而不是编号、标题或表格位置。

AI 不得自行决定业务取舍、优先级、本轮范围、延期、取消或未定业务语义。已有授权决定应如实保留；缺少决定且会改变需求正确性的事项，应明确为待决问题及其影响，而不能静默排除、折中或猜测。此类 Owner decision 未收敛时，Spec 继续澄清而不产生可注册的最终 artifact；普通可逆技术设计选择由 Plan 收敛，不构成 Spec Owner blocker。

### 结果与证明方向

定义用户、业务或系统可观察到的成功结果、重要反例和禁止副作用。

Spec 说明需要证明什么，不规定表结构、接口、测试步骤、测试工具或技术验证方案；这些由 Plan 设计、Do 执行。

## 与后续阶段的边界

| 阶段 | 负责的问题 |
|---|---|
| Spec | 自然语言需求在业务、产品和当前现实中的含义是什么，应形成什么工作流需求。 |
| Plan | 为已收敛的工作流需求选择什么技术架构、实现方式方法和验证方案。 |
| Tasks | 如何依据方案拆分可执行的任务单元。 |
| Do | 如何按方案实现，并以实际证据验证结果。 |
| Ship | 如何归纳本次迭代已实现、已验证、未验证、风险和后续事项。 |

Do 或 Plan 发现的新事实若推翻 Spec 的目标、规则、范围、事实主权或结果语义，应回流 Spec 重新收敛；下游不能静默重定义需求。

## 不负责

Spec 不负责：

- 决定业务 Owner 未确认的范围、优先级、拆分、延期或取消；
- 设计技术架构、数据模型、接口、SQL、事务、索引、类结构、页面或交互实现；
- 拆分 build / verify 任务、任务顺序或执行方式；
- 将通用工程常识、无关 UX 清单或未经证实的推断写成硬性需求；
- 因追求“完整”而扩大到与目标无关的业务域；
- 因实现困难、当前代码存在或证据不足而丢弃已发现的重要目标。

## 完成标准

Spec 在以下条件满足时完成：

1. 已理解业务背景、业务场景和受影响的完整链路；
2. 已保全从可获得输入和证据中发现的重要业务目标、产品目标、功能点和约束；
3. 已区分确认事实、当前现实、冲突、证据缺口、候选推断和待决事项；
4. 已表达与目标相关的业务不变量、非目标或已有范围决定；
5. 已说明成功结果、重要反例和禁止副作用；
6. Plan 可以在不重新猜测需求含义的前提下设计方式方法；
7. 尚未确定且会改变正确性的事项没有被 AI 静默裁决。
