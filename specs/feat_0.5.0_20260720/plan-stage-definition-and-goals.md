# Plan 阶段：定义与目标

## 定义

Plan 阶段将已经收敛的工作流需求，在当前项目的真实条件下理解为一个待解决的系统设计问题，并沉淀为按完整业务需求块组织、可指导落地的技术方案。该方案以业务实现模型为语义主线，并在材料性相关时明确 UI/交互、接口与调用契约、业务逻辑、数据/表结构/字段、SQL/DAO/query、代码与模块结构、事务/并发/性能、Job/运行协作、演进迁移和验证设计。

Spec 已经确认什么结果必须成立、哪些事实与边界不能被猜测、哪些未知仍需要保留。Plan 不按 Spec 的标题、段落或固定字段逐项翻译，也不重新解释业务含义；它从 Spec 全文吸收会改变设计正确性的承诺、关系、场景、规则、事实、反例、约束、未知与证明要求，将它们重新组织为能力、工作面、事实、状态、职责、协作、变化轴和验证义务。

Plan 结合当前项目的框架、架构、模块责任、代码形态、数据与状态、接口、运行路径、既有能力和工程约束推导技术方案。`CLAUDE.md`、`constitution.md`、框架说明、历史材料和当前代码不是 Plan 的复写对象；它们是理解设计空间、判断承接能力和约束方案选择的事实与证据。

## 目标

使 Tasks 和 Do 不必重新猜测以下问题：

- 已确认需求中的多个功能、页面、角色、接口、Job 和外部协作，哪些围绕同一稳定业务能力，哪些具有必须保留的真实差异；
- 系统应以哪些核心概念、权威事实、状态生命周期、职责边界和协作关系承载这些需求；
- 哪些共同规则、权限、数据关系、不变量、外部副作用、一致性和性能约束必须被统一守住；
- 当前系统中哪些 UI、接口、服务、模块、DTO/实体、Mapper/DAO、表/字段、查询、事务、Job、外部调用和验证能力可作为正确承接，哪些只能复用局部机制，哪些与目标冲突、需要改变或缺少证据；
- 对材料性业务块，UI/交互、接口/调用契约、业务逻辑、数据/表结构/字段、SQL/DAO/query、代码与模块结构、事务/并发/性能、运行协作、演进与验证如何共同表达同一个业务实现决策；
- 哪些设计判断可由证据和合理技术推荐收敛，哪些存在真正的架构、公共契约、数据语义、不可逆迁移或外部业务分叉，必须由有权决定者确认；
- 什么可观察事实说明技术方案实现了目标，什么反例、错误结果或禁止副作用说明设计不成立。

## 设计收敛

### 从 Spec 吸收设计信号

Plan 不读取“某一节”才获得某一种设计输入。一个业务目标可能同时隐含状态、权限、外部协作、数据主权、性能和验证要求；一个反例、证据缺口或已有范围决定也可能改变能力边界和设计选择。

Plan 应从 Spec 中任何位置出现的相关语义，识别以下相互关联的设计信号：

- **结果与受影响者**：系统需要承担什么能力，谁通过何种工作面发起、处理、观察或追溯结果；
- **场景、链路与依赖**：哪些触发、判断、协作、状态变化、外部后果、异常和后续路径共同决定设计正确性；
- **规则、事实与边界**：什么是权威事实，哪些关系、权限、责任、非目标和禁止后果不可被技术便利改变；
- **产品与质量要求**：哪些可理解性、效率、恢复、规模、兼容、一致性、安全或可维护性要求会改变系统结构或控制方式；
- **当前现实与覆盖判断**：哪些已有路径已经正确承接，哪些存在冲突，哪些只是局部实现、历史偶然路径或可复用工程机制；
- **未知与证明要求**：哪些结论仍是 evidence gap、候选推断或 Owner decision，什么未来事实才能证明结果和设计控制成立。

这些信号不能按原文顺序、页面、接口、表、文件或技术层次平铺。Plan 要先判断它们之间共享的业务真相、共同不变量、生命周期、外部后果和共同变化轴，再形成设计问题模型。任何会改变设计正确性的 Spec 语义，都必须在该模型和后续技术方案中得到合理去向；不必形成覆盖矩阵，也不能静默丢失、扩大、改写或以技术语言遮蔽。

### 业务实现模型

Plan 将设计问题模型收敛为业务实现模型：稳定能力、核心概念、工作面、权威事实、状态生命周期、职责边界、共同规则、合法变体和协作关系。这是 UI、接口、逻辑、数据、代码和运行设计共享的语义主线。

多个入口、页面或流程共享同一事实、共同不变量、状态生命周期、外部后果、审计要求或共同变化轴时，Plan 应首先判断它们是否是同一能力的不同工作面，而不是分别平铺实现。页面相似、参数相近、DTO 相似、访问同一张表、跨模块调用或代码重复，本身不足以证明应共享设计。

当事实来源、状态模型、权限语义、外部后果、一致性要求或变化方向不同，Plan 应保留真实差异，不以“通用”名义抹平业务语义。一个能力的不同工作面可以拥有不同角色、入口、操作范围、查询投影或展示方式，但不能各自重新解释同一业务事实和共同规则。

### 当前系统中的设计空间

Plan 面向设计问题调查当前系统，而不是盘点文件。它核对当前可达路径、模块责任、依赖方向、UI/交互、数据与状态权威关系、接口与消费者、DTO/实体、表与字段、Mapper/DAO、查询和索引、权限、事务、批处理、外部协作、Job、运行控制、性能边界和可验证性。

当前项目的框架、分层、运行模型、代码形态、质量规则、已有机制和正向实践，应被吸收为设计空间的约束与资产：它们帮助判断何种能力可自然承接，何种 UI、接口、代码结构、数据模型、查询、事务、异步或运行路径具有真实成本，何种结构只是历史偶然实现或已知缺陷。Plan 应据此明确应复用、扩展、修正、替换、新增或保持局部差异的技术承接，而不是只复写现状。它们也不能凌驾于当前需求语义和已证实系统事实之上。

Plan 必须区分：

- 已证实的当前系统事实和已有正确承接；
- 当前实现与已确认需求或设计边界的冲突；
- 可复用的工程机制、局部实现细节或历史偶然路径；
- 规则成立但系统事实、样本或验证不足的证据缺口；
- 基于证据形成的候选设计推断；
- 不能由证据决定、需要有权决定者确认的设计取舍。

当前代码、测试、历史实现、框架惯例或项目规则，只能证明其实际覆盖的事实，不能自动证明它是正确的业务承接或目标设计。

### 抽象、复用与边界

Plan 的抽象目标是统一稳定业务真相与责任，不是制造技术容器、缩短调用链或压缩代码行数。

优先复用或扩展已有语义 owner。只有存在以下至少一种证据时，才考虑形成新的稳定能力边界、模型或抽象：

- 现有边界无法正确表达的新稳定业务事实；
- 独立且长期需要维护的状态生命周期；
- 需要统一承担的权限、事务、幂等、并发、审计或外部副作用一致性责任；
- 多个工作面共享共同规则并具有真实的共同演进压力；
- 既有语义 owner 无法安全承接，继续扩展会混淆事实、状态、职责或依赖边界；
- 已有复杂度确实需要隔离，且隔离后能使关键业务与数据流更清晰而不是更隐蔽。

跨页面、跨模块、传递多个参数或调用链复杂，不是创建 `Context`、`Manager`、`Coordinator`、`Facade`、`Workflow`、通用 Service 或其他中间层的理由。没有稳定事实、独立责任、状态或一致性边界、真实复用压力或复杂度隔离依据的抽象，应保持在现有边界内表达。

### 设计块闭合

Plan 以材料性业务能力或机制形成设计块。每个设计块将以下内容组织为一项相互约束的设计决定，而不是把抽象设计、技术清单和验证方向分散到互不对应的章节：

```text
accepted requirement
→ abstract model and protected truth
→ enforceable business mechanism
→ current-to-target project landing
→ cross-layer concrete design
→ observable scenario evidence
```

设计块应说明当前项目中相关路径和语义 owner、现有证据能证明与不能证明什么、为何现状可复用或与目标冲突，以及目标采用复用、扩展、修正、替换、新增还是保留真实差异。这里的承接方式是帮助形成明确判断的词汇，不是固定枚举字段。每个材料性落点都要说明它保护的事实、不变量或反例，以及受影响的调用者、消费者或历史数据边界。

跨设计块共享的 schema、权限、契约、事务、中间件、演进或验证决定可以集中表达，但必须反向说明服务哪些机制和受保护真相；横向章节不能成为脱离业务机制的技术库存，也不能新增尚未在设计块中解释的设计。

### 跨层一致的具体设计

Plan 先形成业务实现决策，再将其投影到相关技术面。UI/交互、后端业务逻辑、接口与调用契约、代码与模块责任、DTO/Command/Query、DAO/DB/query/SQL、表/字段/约束/索引、权限、外部协作、Job 与运行机制、事务/一致性、性能、演进和验证不是彼此独立的方案清单，而是同一设计判断的不同表现。

每项相关设计需要共同回答：

- 用户或系统从哪些工作面发起、处理、查看或追溯同一业务事实，页面状态、动作、反馈和权限如何表达该事实；
- 业务规则、资格判断、授权、状态转换和副作用由哪个服务、类、模块或责任边界统一承担，哪些 DTO、Command、Query 或接口契约承载何种语义；
- 数据、状态、表/字段、接口和外部结果如何保持同一语义，哪些是权威事实，哪些只是投影、缓存或局部结果；相关 SQL/DAO/query、索引、聚合、批处理和写入如何保证该语义；
- 事务、幂等、锁、条件更新、并发、重跑、消息或回调关联、延迟、失败、未知结果和恢复如何不破坏已确认的结果与边界；
- 当前系统如何从现状演进到目标设计，并如何保留真正必要的迁移、回填、兼容读写、恢复、灰度/回滚语义或运行控制；
- 应采用哪些当前项目可用的测试层级、测试工具、运行观察或验证机制，什么证据能证明业务结果和设计控制真的成立，而不只是证明局部页面、接口或代码路径。

某技术面只要会改变事实或状态含义、权限、外部后果、一致性、兼容与演进、性能成本边界，或者证明是否可信，就是材料性技术面，必须形成当前项目中的具体设计。如果省略后，实施者仍要重新决定会改变正确性的模型、规则、关系、状态、接口、查询、事务、异步或恢复语义，Plan 尚未完成。反之，封闭局部修复不因“完整设计”而默认引入消息、缓存、队列、抽象层、兼容机制、迁移、性能方案或无关技术章节。

Plan 可以明确材料性的类、服务、模块、DTO/Command/Query、Mapper/DAO、SQL/query、表和字段等设计，只要说明其业务语义、责任、约束和理由。命名一个页面、接口、表、Job、中间件或测试类型，不等于完成具体设计。

### PlantUML 设计证据

当设计正确性依赖材料性对象关系或基数、状态生命周期与非法转换、跨系统同步/异步顺序，或者多角色和多入口工作流时，Plan 应使用最小合适的 PlantUML 关系图、状态图、时序图或活动图，使这些决定可被直接审阅。图是设计证据，不是装饰或配额；封闭局部修复在文字已经无歧义时可以没有图。图中的概念、事实、状态、owner 和调用关系必须与正文模型、具体项目落点及场景证明保持同一语义。

### 方案推演与设计确认

Plan 可以形成一个或多个可信设计候选，但不强制多方案。只有候选之间会改变能力边界、事实 owner、状态模型、公共契约、数据语义、外部副作用、一致性模型、不可逆变更、长期演进成本或生产风险接受时，才需要显式推演和比较。

AI 应先用已确认需求、项目事实、当前架构、风险和验证要求收敛设计。无法由证据和合理技术推荐裁决、且会改变设计正确性的 Owner-bearing 取舍，应通过 AskUserQuestion 提出一个高信息量的设计决策包：已确认语义、当前事实、可信候选及其影响、推荐及依据、所需确认。

确认结果必须重新进入对能力边界、工作面、状态、数据、接口、代码、运行、演进和证明的推导。只有确认后出现另一项独立且仍会改变设计正确性的取舍时，才继续澄清。多轮澄清不是固定流程、选项问卷或将局部实现选择推给用户。

AI 不得自行决定长期架构方向、公共契约语义、不可逆迁移、数据模型含义或生产风险接受。无反证的局部技术不确定性不妨碍 Plan 给出明确推荐；DAO/query、lock、transaction、batching、service placement 等可作为推荐约束或验证假设，而不是自动成为 blocker 或 Owner question。证据不足不得伪装为用户偏好、当前项目事实或已完成实现；真正未决的 Owner-bearing 事项必须保留其影响，不能静默选择、折中或下推。

### 结果与证明方向

Plan 定义技术方案如何支持 Spec 的成功结果、重要反例和禁止副作用，并明确需要验证的事实、边界和风险控制。

Plan 应设计验证方式：明确关键场景、反例、测试层级、可使用的现有测试工具或运行验证机制、需观察的迁移/并发/性能/外部协作事实，以及每项证据能证明的范围。Plan 只规定方案应产生什么证据；不把实际执行过的命令、已通过的测试、已完成的迁移或运行观察写成事实。局部编译、静态检查、接口成功、页面截图、mock 或孤立测试，只能证明其直接观察到的局部事实。

### Reviewer 独立设计基线与反例

Reviewer 不以候选 Plan 已经命名的模型、技术面或章节作为完整性基线。它先依据 accepted Spec、已确认决定、相关项目事实和硬约束，独立形成使材料性结果可实现的最低设计义务：需要保护的事实与不变量、状态和责任、current-to-target 承接、不可省略的具体技术面及证明方向。这个基线不是替代方案或通用 checklist；候选可以采用不同路线，只要同样关闭承诺和反例。

随后 Reviewer 构造一个完全遵循候选 Plan 的最小合理实现，检验它是否仍可能使承诺失败、禁止结果可达、事实或历史丢失、状态或权限被绕过、恢复不安全、跨层语义矛盾，或者迫使实施者重新选择会改变正确性的设计语义。只有能形成这种具体失败场景的缺口才是材料 finding；缺少偏好标题、表格、术语、图或无关技术面本身不是缺陷。

## 与后续阶段的边界

| 阶段 | 负责的问题 |
|---|---|
| Spec | 自然语言需求在业务、产品和当前现实中的含义是什么，应形成什么工作流需求。 |
| Plan | 已收敛的工作流需求在当前项目中应形成什么业务实现模型和完整技术方案，包括材料性的 UI、接口、逻辑、数据、代码、运行、演进与验证设计。 |
| Tasks | 如何将已定技术方案按业务块内有关联的 build / verify 责任拆分，而不重新裁决设计语义。 |
| Do | 如何在方案边界内采用项目既有具体语法、文件编辑、migration 格式和局部机械实现落地，并以实际证据验证结果。 |
| Ship | 如何归纳本次迭代已实现、已验证、未验证、风险和后续事项。 |

Plan 或 Do 发现的新事实若推翻 Spec 的目标、规则、范围、事实主权或结果语义，应回流 Spec 重新收敛；下游不能静默重定义需求。Do 发现的新事实若推翻技术方案，应回流 Plan 重新收敛；不能通过局部实现静默改变表/字段、接口、状态、事务或质量语义。Plan 发现的设计取舍在不改变 Spec 语义时由 Plan 收敛；若该取舍实际改变 Spec 语义，也应回流 Spec。

## 不负责

Plan 不负责：

- 重新裁决业务目标、范围、优先级、延期、取消或 Owner 未确认的需求语义；
- 复写 `CLAUDE.md`、`constitution.md`、框架说明、代码目录、历史材料或通用工程规范；
- 脱离业务实现模型，将页面、接口、表、类、文件、模块或当前代码路径机械平铺为设计方案；
- 因技术便利、跨页面复杂性、代码相似或未来假设创建无语义 owner 的 Context、Manager、Coordinator、Facade、Workflow、Wrapper 或通用层；
- 将证据缺口伪装为当前系统事实、实现缺口、用户偏好、已完成实现或确定设计；
- 把技术方案退化为文件级待办、Task 分配、执行排序、逐行代码、函数体、可直接复制的 patch、Builder 操作指令、命令清单、已完成验证结论，或发布/回滚/值班 runbook；
- 因追求抽象或“完整架构”而扩大到与目标无关的平台、领域、基础设施或未来需求。

## 完成标准

Plan 在以下条件满足时完成：

1. 已从 Spec 的全部相关语义中吸收会改变设计正确性的信号，并将其重构为设计问题模型，而不是按章节、页面、接口或文件机械映射；
2. 已识别稳定能力、工作面、核心概念、权威事实、状态生命周期、共同规则、合法变体和必须保留的真实差异；
3. 已结合当前项目真实框架、架构、模块责任、代码形态、数据/状态/接口、运行路径、既有能力和工程约束，形成证据支持的当前—目标技术方案；
4. 已明确应复用、扩展、归并、修正、隔离、新增或保持局部差异的 UI、接口、服务/模块、代码结构、数据/表字段、DAO/query、事务、Job 和验证能力，且没有将偶然实现、历史缺陷或证据不足误作设计依据；
5. 已形成跨 UI、接口、业务逻辑、代码结构、数据/表字段、SQL/DAO/query、外部协作、运行、一致性、性能、演进和验证相互一致的材料性设计决策，并只覆盖需求相关层面；
6. 不存在仅因页面、模块、代码相似或复杂性而引入的无事实 owner、独立责任、状态、一致性边界或真实复用压力的抽象；
7. 已区分已证实设计事实、候选设计、已有正确承接、当前实现冲突、证据缺口、验证假设、设计 blocker 与 Owner-bearing 设计取舍；
8. 尚未确定且会改变设计正确性的事项没有被 AI 静默裁决；必要的确认已经被吸收并重新推导受影响业务块的 UI、接口、数据、代码、运行和证明方案；
9. 已说明技术方案如何支持成功结果、避免重要反例和禁止副作用，以及应由何种测试、运行观察或可验证事实证明这一点；
10. Tasks 和 Do 可以在不重新猜测需求含义、业务实现模型、关键设计理由、表/字段/接口/代码承接方式、质量约束或跨层边界的前提下推进。
